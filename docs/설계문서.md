## 1. 개요

### 1.1 배경

개인 카페에서 Excel로 관리하던 근무시간·급여 기록을, 여러 매장과 여러 사용자가 동시에 쓸 수 있는 웹 서비스로 확장한다.

### 1.2 해결하려는 문제

| 문제 | 현재(Excel) | 목표(웹 서비스) |
|---|---|---|
| 근무시간 집계 | 개인이 수기 입력 | 달력에서 입력 → 자동 집계 |
| 주휴수당 계산 | 매번 수동 계산, 실수 발생 | 주 단위 자동 계산 |
| 시급 변경 이력 | 덮어쓰기 되어 과거 추적 불가 | 기간별 이력 보존 |
| 매장 단위 인건비 | 파일을 모아야 확인 가능 | 대시보드에서 즉시 확인 |
| 근무기록 신뢰성 | 검증 절차 없음 | 제출 → 승인/반려 워크플로 |

### 1.3 범위 (MVP)

포함: 회원가입/로그인, 매장·구성원 관리, 시급 이력, 근무기록 입력·승인, 주휴수당 포함 월 급여 계산, 공휴일 표시, 역할별 대시보드.

제외(향후): 근무 스케줄 편성, 알림(푸시/카카오), 다중 매장 동시 근무, 4대보험·세금 공제, 급여명세서 PDF 발행, 급여 실지급 연동.

## 2. 사용자 역할과 권한

### 2.1 역할 정의

```
OWNER (사장님)  ─ stores.owner_id 로 식별. 자신이 소유한 매장 전체 관리
  └ MANAGER (매니저) ─ store_members.role = 'MANAGER'. 배정된 매장만 관리
  └ EMPLOYEE (알바생) ─ store_members.role = 'EMPLOYEE'. 본인 데이터만
```

> **설계 결정 #1** — OWNER는 `store_members`에 넣지 않고 `stores.owner_id`로만 식별한다.
> 이유: 사장님은 "매장에 소속된 근로자"가 아니라 "매장의 소유자"이므로 개념이 다르고,
> `store_members`에 OWNER를 넣으면 시급·근무기록 스키마가 사장님에게도 강제된다.
> 단, 사장님이 직접 근무도 하는 경우(1인 카페 등)에는 본인을 EMPLOYEE로 추가 등록할 수 있다.
> 즉 **한 사람이 특정 매장에서 owner이면서 동시에 EMPLOYEE 멤버일 수 있다.**

### 2.2 권한 매트릭스

| 기능 | EMPLOYEE | MANAGER | OWNER |
|---|:---:|:---:|:---:|
| 본인 근무기록 조회 | O | O | O |
| 본인 근무기록 입력·수정 | O (DRAFT/REJECTED만) | O | O |
| 본인 급여 조회 | O | O | O |
| 다른 직원 근무기록 조회 | X | 담당 매장만 | 소유 매장 전체 |
| 근무기록 승인/반려 | X | 담당 매장만 | 소유 매장 전체 |
| 직원 시급 조회 | X | 담당 매장만 | 소유 매장 전체 |
| 직원 시급 변경 | X | X (설계 결정 #2) | O |
| 직원 등록·해지 | X | 담당 매장만 | 소유 매장 전체 |
| 매니저 등록·담당 설정 | X | X | O |
| 매장 생성·수정·삭제 | X | X | O |
| 매장별 인건비 조회 | X | 담당 매장만 | 소유 매장 전체 |
| 전체 매장 통합 통계 | X | X | O |

> **설계 결정 #2** — 원문의 "매니저: 시급 변경 제한적"은 MVP에서 **불가(X)** 로 단순화한다.
> 시급은 금전 채무에 직결되고, "제한적"의 범위(상한선? 승인 필요?)를 정의하면 RLS가 복잡해진다.
> 매니저에게 필요한 것은 대개 "시급 변경 요청"이므로, 향후 `wage_change_requests` 테이블로 별도 구현한다.

### 2.3 역할별 핵심 시나리오

**알바생**: 로그인 → 달력에서 오늘 근무 입력(출근/퇴근/휴게) → 주간 누적시간·주휴 충족 여부 확인 → 월말 제출 → 예상 급여 확인

**매니저**: 로그인 → 담당 매장 대시보드에서 미승인 건수 확인 → 승인 대기 목록에서 일괄 검토 → 이상 건 반려(사유 입력) → 매장 월 인건비 확인

**사장님**: 매장 생성 → 매니저 초대·배정 → 직원 등록 및 시급 설정 → 월별 매장별 인건비 비교 → 급여 확정

## 4. 데이터베이스 설계

### 4.1 ERD

`docs/erd.mermaid` 참조. 요약:

```
auth.users 1─1 profiles
profiles 1─N stores (owner_id)
stores 1─N store_members N─1 profiles
store_members 1─N wage_history
store_members 1─N work_records
store_members 1─N weekly_summaries
store_members 1─N payrolls
holidays (독립 테이블, 전역 참조)
```

### 4.2 ENUM 타입

| 타입 | 값 |
|---|---|
| `member_role` | `MANAGER`, `EMPLOYEE` |
| `member_status` | `ACTIVE`, `INACTIVE` |
| `work_status` | `DRAFT`, `SUBMITTED`, `APPROVED`, `REJECTED` |
| `payroll_status` | `CALCULATED`, `CONFIRMED`, `PAID` |
| `holiday_type` | `PUBLIC`, `SUBSTITUTE`, `TEMPORARY` |

### 4.3 테이블 명세

#### profiles — 사용자 기본 정보

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK, FK → auth.users(id) ON DELETE CASCADE | Supabase Auth 사용자 ID |
| name | text | NOT NULL | 실명 |
| email | text | NOT NULL, UNIQUE | 로그인 이메일 |
| phone | text | NULL | 연락처(매장 관리용) |
| created_at | timestamptz | DEFAULT now() | |
| updated_at | timestamptz | DEFAULT now() | 트리거로 자동 갱신 |

- 회원가입 시 `auth.users` INSERT 트리거로 자동 생성한다(§4.5).
- **역할 컬럼을 두지 않는다.** 역할은 매장별로 달라질 수 있으므로 `store_members`에 둔다.

#### stores — 매장

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK, DEFAULT gen_random_uuid() | |
| name | text | NOT NULL | 매장명 |
| owner_id | uuid | NOT NULL, FK → profiles(id) | 사장님 |
| address | text | NULL | |
| week_start_day | smallint | NOT NULL DEFAULT 1 | 주 시작 요일(1=월요일). 주휴 계산 기준 |
| is_active | boolean | NOT NULL DEFAULT true | 폐점 시 false |
| created_at | timestamptz | DEFAULT now() | |

- `week_start_day`는 원문에 없던 추가 컬럼이다. 주휴수당은 "주" 단위 계산이므로 매장마다 주의 시작 요일이 다르면 결과가 달라진다. 이를 매장 설정으로 명시한다.

#### store_members — 매장-사용자 소속 관계

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK | |
| store_id | uuid | NOT NULL, FK → stores(id) ON DELETE CASCADE | |
| user_id | uuid | NOT NULL, FK → profiles(id) ON DELETE CASCADE | |
| role | member_role | NOT NULL | MANAGER / EMPLOYEE |
| status | member_status | NOT NULL DEFAULT 'ACTIVE' | 퇴사 시 INACTIVE |
| joined_at | date | NOT NULL DEFAULT current_date | 입사일 |
| left_at | date | NULL | 퇴사일 |
| created_at | timestamptz | DEFAULT now() | |

- UNIQUE(store_id, user_id, role) — 같은 매장에서 같은 역할로 중복 등록 방지.
- 모든 근무·급여 데이터는 `user_id`가 아니라 **`store_member_id`를 FK로 잡는다.** 한 사람이 여러 매장에 소속될 수 있으므로, "누가"가 아니라 "어느 매장의 누구"가 급여의 단위다.
- 퇴사자는 행을 삭제하지 않고 `status='INACTIVE'`로 둔다(과거 급여 이력 보존).

#### wage_history — 시급 변경 이력

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK | |
| store_member_id | uuid | NOT NULL, FK → store_members(id) ON DELETE CASCADE | |
| hourly_wage | integer | NOT NULL, CHECK (hourly_wage >= 10030) | 원 단위 정수. 2026년 최저시급 하한 |
| effective_from | date | NOT NULL | 적용 시작일(포함) |
| effective_to | date | NULL | 적용 종료일(포함). NULL = 현재 적용 중 |
| memo | text | NULL | 변경 사유 |
| created_by | uuid | FK → profiles(id) | 변경한 사람 |
| created_at | timestamptz | DEFAULT now() | |

- **금액은 `numeric`이 아닌 `integer`(원 단위)로 저장한다.** 부동소수점 오차를 원천 차단한다.
- **기간 중첩 방지**: `EXCLUDE USING gist (store_member_id WITH =, daterange(effective_from, effective_to, '[]') WITH &&)` 제약을 건다(`btree_gist` 확장 필요). 같은 날짜에 시급이 둘인 상황을 DB 레벨에서 막는다.
- 시급 변경 시: 기존 행의 `effective_to`를 (신규 시작일 - 1일)로 UPDATE → 신규 행 INSERT. 이 두 동작은 함수 하나로 묶어 원자적으로 처리한다.
- CHECK 제약의 최저시급 하한(10,030원)은 2026년 기준이다. 매년 갱신이 필요하므로, 하드코딩 대신 `settings` 테이블로 뺄지는 §10 참조.

#### work_records — 일별 근무기록

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK | |
| store_member_id | uuid | NOT NULL, FK → store_members(id) ON DELETE CASCADE | |
| work_date | date | NOT NULL | 근무 시작일 기준 |
| start_time | time | NOT NULL | 출근 시각 |
| end_time | time | NOT NULL | 퇴근 시각 |
| crosses_midnight | boolean | NOT NULL DEFAULT false | 익일 퇴근 여부 |
| break_minutes | integer | NOT NULL DEFAULT 0, CHECK (>= 0) | 휴게시간 |
| work_minutes | integer | NOT NULL, CHECK (> 0) | 실 근무 분 = 총 체류 - 휴게 |
| status | work_status | NOT NULL DEFAULT 'DRAFT' | |
| memo | text | NULL | 알바생 메모 |
| reject_reason | text | NULL | 반려 사유 |
| submitted_at | timestamptz | NULL | |
| approved_by | uuid | NULL, FK → profiles(id) | |
| approved_at | timestamptz | NULL | |
| created_at / updated_at | timestamptz | DEFAULT now() | |

- UNIQUE(store_member_id, work_date) — 하루 1건. (하루 2회 출근이 필요하면 §10 참조)
- **`crosses_midnight`는 원문에 없던 추가 컬럼이다.** 카페 마감 근무는 22:00~01:00처럼 자정을 넘길 수 있고, 이때 `end_time < start_time`이 되어 단순 뺄셈이 음수가 된다. 플래그로 명시하고 `work_minutes`는 트리거로 계산한다.
- `work_minutes`는 앱이 아니라 **DB 트리거에서 계산**한다. 클라이언트를 신뢰하지 않는다.
- 상태 전이:
  ```
  DRAFT ──제출──> SUBMITTED ──승인──> APPROVED
                      │
                      └──반려──> REJECTED ──수정──> SUBMITTED
  ```
  - 알바생은 `DRAFT`, `REJECTED` 상태에서만 수정·삭제할 수 있다.
  - `APPROVED` 건의 수정은 매니저/사장님만 가능하다(수정 시 급여 재계산 필요).
  - 급여가 `CONFIRMED`된 월의 근무기록은 잠근다(트리거로 차단).

#### weekly_summaries — 주간 집계 (추가 테이블)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | uuid | PK |
| store_member_id | uuid | FK → store_members(id) |
| week_start | date | 주 시작일(매장 `week_start_day` 기준) |
| week_end | date | 주 종료일 |
| work_minutes | integer | 해당 주 승인된 총 근무 분 |
| is_eligible | boolean | 주 15시간 이상 충족 여부 |
| allowance_minutes | integer | 주휴 환산 분(§5) |
| calculated_at | timestamptz | |

> **설계 결정 #3** — 원문에 없던 테이블을 추가한다.
> 이유: 주휴수당은 "주" 단위인데 급여는 "월" 단위라, 월 첫 주가 전월과 걸치는 문제(§5.3)가 생긴다.
> 주간 집계를 물리 테이블로 남기면 (1) 전월 마지막 주를 조회 한 번으로 가져오고,
> (2) "왜 이 금액이 나왔는지" 직원에게 근거를 보여줄 수 있으며, (3) 재계산이 멱등해진다.
> UNIQUE(store_member_id, week_start).

#### payrolls — 월별 급여 결과

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | uuid | PK |
| store_member_id | uuid | FK → store_members(id) |
| year | integer | CHECK (2020~2100) |
| month | integer | CHECK (1~12) |
| work_minutes | integer | 당월 총 근무 분(승인 건만) |
| allowance_minutes | integer | 주휴 환산 분 합계 |
| base_pay | integer | 기본급(원) |
| allowance_pay | integer | 주휴수당(원) |
| total_pay | integer | 합계(원) |
| wage_breakdown | jsonb | 적용된 시급 구간별 내역(감사 추적용) |
| status | payroll_status | CALCULATED / CONFIRMED / PAID |
| calculated_at | timestamptz | |
| confirmed_by | uuid | FK → profiles(id) |
| confirmed_at | timestamptz | |

- UNIQUE(store_member_id, year, month).
- 원문의 `hourly_wage` 단일 컬럼은 **삭제**한다. 월 중간에 시급이 바뀌면 단일 값으로 표현할 수 없다. 대신 `wage_breakdown` jsonb에 `[{from, to, wage, minutes, pay}]` 형태로 구간별 내역을 남긴다.
- `CONFIRMED` 이후에는 재계산을 막고, 정정이 필요하면 별도 조정 행(향후 `payroll_adjustments`)으로 처리한다.

#### holidays — 공휴일

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | uuid | PK |
| holiday_date | date | UNIQUE |
| name | text | 예: 설날, 대체공휴일 |
| type | holiday_type | PUBLIC / SUBSTITUTE / TEMPORARY |
| is_public_holiday | boolean | 유급 공휴일 여부 |
| source | text | 'data.go.kr' 등 |

## 5. 급여 계산 규칙

### 5.1 법적 근거

주휴수당은 근로기준법 제55조에 따라 **1주 소정근로시간 15시간 이상**이고 **소정근로일을 개근**한 근로자에게 지급한다.

표준 계산식:

```
주휴수당 = 시급 × (주 소정근로시간 ÷ 40) × 8
```

`(주간시간 ÷ 40) × 8 = 주간시간 ÷ 5` 이므로, 원문의 **"5시간 환산"은 법정 계산식과 동일**하다.

### 5.2 계산 규칙 (확정)

```
주간 근무시간 W (단위: 시간)

W < 15        → 주휴 환산시간 = 0
15 ≤ W ≤ 40   → 주휴 환산시간 = W ÷ 5
W > 40        → 주휴 환산시간 = 8        ← 상한 (원문에 없던 규칙, 추가)
```

> **설계 결정 #4** — 40시간 초과분에 대한 상한 8시간을 추가한다.
> 원문 규칙(`W ÷ 5`)을 그대로 적용하면 주 50시간 근무 시 환산 10시간이 되어 법정 상한(8시간)을 초과한다.
> 주휴수당은 "소정근로시간" 기준이며 연장근로는 포함하지 않으므로 8시간이 상한이다.

월 급여:

```
기본급     = Σ (일별 근무시간 × 그 날짜에 유효한 시급)
주휴수당   = Σ (주별 환산시간 × 그 주에 유효한 시급)
총 지급액  = 기본급 + 주휴수당
```

- 시급은 `wage_history`에서 **근무 날짜 기준**으로 조회한다(월말 시급 일괄 적용 아님).
- 주휴수당 계산 시 적용 시급은 **해당 주의 마지막 근무일 시급**을 쓴다(§10에서 재확인 필요).
- 원 단위 미만은 **절사(floor)** 한다. 계산 순서: 시간 → 분 단위 정수 연산 → 마지막에 원 단위 절사.

### 5.3 월 경계 처리

주는 월을 넘나든다. 원문 규칙을 그대로 채택한다:

- **달력·기본급 표시**: 당월에 속한 날짜의 근무시간만 사용한다.
- **주휴 판단**: 주 전체(전월 마지막 주 + 당월 첫 주)를 합산해 15시간 충족 여부를 본다.

예시 — 8월 1일(토)이 주의 마지막 날인 경우:

| 항목 | 값 |
|---|---|
| 7/27(월)~7/31(금) 근무 | 14시간 |
| 8/1(토) 근무 | 4시간 |
| 주 합계 | 18시간 → 15시간 이상 충족 |
| 주휴 환산 | 18 ÷ 5 = 3.6시간 |

> **확정 규칙 A** — 주휴수당은 **주가 끝나는 날짜(`week_end`)가 속한 달**에 귀속시킨다.
> 위 예시의 3.6시간은 **8월 급여**에 들어간다.
> 구현: `payrolls` 계산 시 `weekly_summaries` 중 `extract(month from week_end) = 대상월` 인 행만 합산한다.
> 이 규칙은 한 줄로 끝나고, 이미 확정된 전월 급여를 소급 수정할 일이 없다.

### 5.3.1 퇴사 주 처리 (확정 규칙 B)

퇴사 주는 **퇴사 당일(`store_members.left_at`)까지만 합산**한다.

- 주 집계 범위 = `[week_start, min(week_end, left_at)]`
- 그 범위의 근무시간이 900분(15시간) 이상이면 **정상 규칙대로 주휴수당을 지급**한다(÷5, 상한 8시간).
- 900분 미만이면 0.
- 입사 첫 주도 대칭적으로 처리한다: `[max(week_start, joined_at), week_end]`.

예시 — 퇴사일이 수요일(8/12)이고 주 시작이 월요일인 경우:

| 항목 | 값 |
|---|---|
| 8/10(월) 6시간 + 8/11(화) 6시간 + 8/12(수) 5시간 | 17시간 |
| 8/13(목)~8/16(일) | 근무 없음 (이미 퇴사) |
| 주 합계 | 17시간 → 15시간 이상 충족 |
| 주휴 환산 | 17 ÷ 5 = 3.4시간 |

**규칙 A와 B가 충돌하는 경우** — 7/28(화) 퇴사자의 7/27~8/2 주는 규칙 A만 보면 주 종료일이 8/2라 8월 귀속이 되지만,
그러면 8월 근무가 하나도 없는 사람에게 8월 주휴수당만 뜨게 된다.
따라서 **귀속 월은 재직 범위로 자른 종료일(`rangeTo = min(weekEnd, leftAt)`)의 월**로 정한다.
재직 중인 직원은 `rangeTo = weekEnd`이므로 규칙 A와 완전히 동일하게 동작한다.

> **참고** — 실무·판례상 "퇴사 주의 주휴수당은 다음 주까지 근속해야 발생한다"는 해석도 있어
> 이 규칙(퇴사 주도 15시간 충족 시 지급)은 근로자에게 유리한 쪽이다.
> 서비스가 **예상 급여 안내** 목적이므로 이 방식을 채택하되,
> 실제 지급 시에는 노무 확인을 거치도록 화면에 안내 문구를 둔다.

### 5.4 경계 케이스 검증

| # | 상황 | 처리 |
|---|---|---|
| 1 | 주 14시간 59분 | 환산 0. 15시간은 **분 단위**로 판정(899분 < 900분) |
| 2 | 주 정확히 15시간 | 환산 3시간 |
| 3 | 주 45시간 | 환산 **8시간**(상한 적용, 9시간 아님) |
| 4 | 월 중 시급 변경 (8/1 10,030 → 8/15 11,000) | 8/1~8/14는 10,030, 8/15~는 11,000. `wage_breakdown`에 두 구간 기록 |
| 5 | 승인되지 않은 근무기록 | 급여 계산에서 **제외**. 대시보드에는 "미승인 N건, 예상 +X원"으로 별도 표시 |
| 6 | 자정 넘김 (22:00~01:00, 휴게 0) | `crosses_midnight=true`, work_minutes=180. 근무일은 **출근일(전날)** 기준 |
| 7 | 입사 첫 주가 주 중간에 시작 | `[max(week_start, joined_at), week_end]` 범위만 합산. 15시간 미달이면 환산 0 |
| 8 | 퇴사 주 (수요일 퇴사, 17시간) | `[week_start, left_at]` 범위 합산 → 15시간 충족 → 환산 3.4시간 (§5.3.1) |
| 9 | 반올림 | 분 단위 정수 유지, 최종 금액만 floor. 예: 3.6h × 10,030 = 36,108원 |
| 10 | 급여 확정 후 근무기록 수정 시도 | 트리거로 차단, 에러 메시지 반환 |

### 5.5 계산 알고리즘 (의사코드)

```
calculate_payroll(store_member_id, year, month):
  1. 대상 기간 = [year-month-01, 말일]
  2. 대상 기간과 겹치는 모든 "주"를 매장 week_start_day 기준으로 나열
     (전월 마지막 주 ~ 익월 첫 주까지 여유 있게)
  3. 각 주에 대해:
       a. 재직 범위로 자른다 (규칙 B)
            from = max(week_start, joined_at)
            to   = min(week_end,   left_at ?? week_end)
          from > to 이면 그 주는 건너뛴다
       b. [from, to] 의 APPROVED work_records 합산 → week_minutes
       c. is_eligible = (week_minutes >= 900)
       d. allowance_minutes = eligible ? min(floor(week_minutes / 5), 480) : 0
       e. weekly_summaries UPSERT
  4. 기본급 = Σ over 당월 근무일 (work_minutes / 60 × wage_at(work_date))
  5. 주휴수당 = Σ over (week_end 의 월 == 대상 월인 주) (allowance_minutes / 60 × wage)   ← 규칙 A
     적용 시급 = 그 주의 마지막 근무일 시급 (규칙 C)
  6. payrolls UPSERT (status = CALCULATED)
```

Edge Function `calculate-payroll`으로 구현하며, **멱등**해야 한다(같은 입력 → 같은 결과, 여러 번 호출해도 안전).

## 6. 인가(RLS) 설계

### 6.1 원칙

- 모든 테이블에 `ENABLE ROW LEVEL SECURITY`를 켜고, **명시적으로 허용한 것만 통과**시킨다.
- 프론트엔드는 `anon key`로 DB에 직접 접근하므로, RLS가 사실상 유일한 방어선이다. 클라이언트 코드의 조건문은 UX용일 뿐 보안이 아니다.

### 6.2 무한 재귀 함정 (필독)

`store_members` 테이블의 정책에서 다시 `store_members`를 SELECT 하면 PostgreSQL이 정책을 재귀 평가하여
`infinite recursion detected in policy for relation "store_members"` 에러가 난다.
Supabase 프로젝트에서 가장 흔하게 막히는 지점이다.

해결: 소속 확인 로직을 **`SECURITY DEFINER` 함수**로 빼서 RLS를 우회시킨다.

```sql
create or replace function public.is_store_manager(p_store_id uuid)
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select exists (
    select 1 from store_members
    where store_id = p_store_id
      and user_id = auth.uid()
      and role = 'MANAGER'
      and status = 'ACTIVE'
  );
$$;
```

### 6.3 헬퍼 함수 목록

| 함수 | 반환 | 용도 |
|---|---|---|
| `is_store_owner(store_id)` | boolean | `stores.owner_id = auth.uid()` |
| `is_store_manager(store_id)` | boolean | 해당 매장 ACTIVE 매니저인가 |
| `can_manage_store(store_id)` | boolean | owner OR manager |
| `owns_member(member_id)` | boolean | 그 store_member 행이 본인인가 |
| `can_manage_member(member_id)` | boolean | 그 멤버가 속한 매장을 관리할 수 있는가 |

### 6.4 테이블별 정책 요약

| 테이블 | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| profiles | 본인 + 같은 매장 관리자 | 본인(트리거 자동) | 본인 | X |
| stores | owner 또는 소속 멤버 | `owner_id = auth.uid()` | owner | owner |
| store_members | 본인 행 또는 `can_manage_store` | `can_manage_store` (MANAGER 추가는 owner만) | `can_manage_store` | owner |
| wage_history | `owns_member` 또는 `can_manage_store` | **owner만** | **owner만** | X |
| work_records | `owns_member` 또는 `can_manage_member` | `owns_member` 또는 `can_manage_member` | 본인은 DRAFT/REJECTED만, 관리자는 전체 | 본인은 DRAFT만 |
| weekly_summaries | `owns_member` 또는 `can_manage_member` | service_role만 | service_role만 | X |
| payrolls | `owns_member` 또는 `can_manage_member` | service_role만 | 확정은 owner만 | X |
| holidays | 인증 사용자 전체 | service_role만 | service_role만 | service_role만 |

전체 SQL은 `supabase/migrations/0001_init.sql`에 있다.

### 6.5 검증 방법

배포 전 반드시 다음을 직접 테스트한다:

1. 알바생 A 계정으로 로그인 → 알바생 B의 `work_records`를 `select` → **0행**이 나와야 한다(에러가 아니라 0행).
2. 알바생 계정으로 `wage_history` INSERT 시도 → **거부**되어야 한다.
3. 매장 X 매니저 계정으로 매장 Y 직원 조회 → **0행**.
4. 사장님 계정으로 타인 소유 매장 조회 → **0행**.
5. `store_members` 조회 시 무한 재귀 에러가 나지 않아야 한다.

```
│  └─ 0003_seed.sql            개발용 시드 데이터
└─ functions/
   ├─ calculate-payroll/
   └─ sync-holidays/
```

## 8. 공휴일 동기화

```
공공데이터포털 특일 정보 API
        │  (Edge Function 내부에서만 호출, 인증키는 서버 환경변수)
        ▼
Supabase Edge Function: sync-holidays
        │  upsert on conflict (holiday_date)
        ▼
holidays 테이블
        │  RLS: 인증 사용자 SELECT 허용
        ▼
React (TanStack Query, staleTime 24h)
```

- 프론트에서 공공 API를 직접 호출하지 않는다. 인증키 노출 + CORS 문제를 모두 피한다.
- 실행 주기: `pg_cron`으로 매일 1회 + 연말(12월)에 익년치 일괄 동기화.
- API 실패 시 기존 데이터를 유지한다(빈 응답으로 덮어쓰지 않도록 `synced_at`만 갱신하고 삭제는 하지 않는다).

## 9. 개발 순서

각 단계는 **끝나면 눈으로 확인 가능한 결과물**이 나오도록 잘랐다.

| # | 단계 | 완료 기준 |
|---|---|---|
| 1 | Vite + React + TS 프로젝트 생성, Tailwind·Router·TanStack Query 설정 | `npm run dev`로 빈 레이아웃이 뜬다 |
| 2 | Supabase 프로젝트 생성, `.env` 연결, `supabase.ts` 클라이언트 | 콘솔에서 세션 객체가 찍힌다 |
| 3 | **0001_init.sql 적용** (타입·테이블·인덱스·트리거) | Supabase Table Editor에 7개 테이블이 보인다 |
| 4 | **0002_rls.sql 적용** + §6.5 검증 5종 통과 | 타 계정 데이터가 0행으로 나온다 |
| 5 | 회원가입/로그인/로그아웃, `profiles` 자동 생성 확인 | 가입하면 profiles 행이 생긴다 |
| 6 | 사장님: 매장 생성·목록 | 매장을 만들고 목록에서 본다 |
| 7 | 사장님: 직원/매니저 등록(이메일로 초대 또는 직접 추가) | store_members 행이 생긴다 |
| 8 | 사장님: 시급 설정 + 이력 조회 | 시급을 바꾸면 이전 행이 마감된다 |
| 9 | 공휴일 Edge Function + 테이블 저장 | 2026년 공휴일이 DB에 들어온다 |
| 10 | 알바생: 근무 달력 (공휴일 표시, 빈 셀) | 월 그리드가 그려진다 |
| 11 | 알바생: 근무기록 입력·수정·제출 | 달력 셀에 시간과 상태가 표시된다 |
| 12 | 매니저: 승인 대기 목록, 승인/반려 | 상태가 APPROVED로 바뀐다 |
| 13 | **급여 계산 Edge Function** (§5 전체 규칙 + §5.4 케이스 테스트) | 예제 10건이 손계산과 일치한다 |
| 14 | 알바생: 급여 화면 + 계산 근거 표 | 주별 근거가 펼쳐진다 |
| 15 | 매니저/사장님 대시보드, 인건비 집계 | 매장 월 인건비가 나온다 |
| 16 | Cloudflare Pages 배포 + 환경변수 설정 | 공개 URL에서 동작한다 |

**13단계가 이 프로젝트의 핵심이자 가장 어려운 부분이다.** 여기에 시간을 가장 많이 배분하고, 반드시 테스트 케이스를 먼저 작성한 뒤 구현한다.

## 10. 미결정 사항 (개발 시작 전 확정 필요)

| # | 항목 | 결정 | 상태 |
|---|---|---|---|
| A | 월 경계 주휴수당의 귀속 월 (§5.3) | **주 종료일(`week_end`)이 속한 달**에 귀속 | ✅ 확정 |
| B | 퇴사 주의 주휴수당 (§5.3.1) | **퇴사 당일까지만 합산**, 15시간 충족 시 정상 지급 | ✅ 확정 |
| C | 주휴수당 적용 시급 (주 중 시급 변경 시) | **주의 마지막 근무일 시급** | ✅ 확정 |
| D | 하루 2회 출근(스플릿 근무) | MVP는 1일 1건 제한. 필요 시 UNIQUE 제약 해제 | ✅ 확정 |
| E | 최저시급 하한 CHECK | 2026년 10,030원 하드코딩, 연말 마이그레이션으로 갱신 | ✅ 확정 |
| F | 공휴일 근무 가산수당 | MVP 제외 (5인 이상 사업장만 의무) | ✅ 확정 |
| G | 직원 등록 방식 | 알바생이 매장 코드 입력 (`stores.join_code`) | ✅ 확정 |
| H | 시간대 | 항상 KST. `date`/`time` 타입 사용, `timestamptz`는 감사 컬럼에만 | ✅ 확정 |

> B 규칙 주의 — 실무·판례상 "퇴사 주 주휴는 다음 주 근속 시 발생"이라는 해석도 있다.
> 채택한 규칙은 근로자에게 유리한 쪽이므로, 실제 지급 전 노무 확인 안내를 화면에 표시한다.

## 부록 B: 스키마 검증 결과

`0001_init.sql` + `0002_rls.sql`을 **PostgreSQL 16 실제 인스턴스에 적용해 동작을 확인**했다
(Supabase의 `auth.users` / `auth.uid()`는 스텁으로 대체).

| # | 검증 항목 | 결과 |
|---|---|---|
| 1 | 두 마이그레이션 무오류 적용 | 통과 |
| 2 | `auth.users` INSERT → `profiles` 자동 생성 | 통과 (5/5) |
| 3 | 시급 적용 기간 중첩 INSERT 차단 | 통과 (`excl_wage_overlap` 위반) |
| 4 | 최저시급(10,030원) 미만 INSERT 차단 | 통과 (CHECK 위반) |
| 5 | `wage_at()` 날짜별 시급 조회 | 통과 (8/10→10,030, 8/20→11,000) |
| 6 | `work_minutes` 계산 (09:00–18:00, 휴게 60분) | 통과 (480분) |
| 7 | 자정 넘김 계산 (22:00–01:00) | 통과 (180분) |
| 8 | 자정 넘김인데 플래그 누락 | 통과 (안내 메시지와 함께 거부) |
| 9 | 하루 2건 중복 입력 차단 | 통과 (UNIQUE 위반) |
| 10 | **`store_members` 조회 시 무한 재귀** | **에러 없음** — SECURITY DEFINER 방식 유효 |

| 12 | 알바가 시급 INSERT 시도 | 통과 (RLS 위반으로 거부) |
| 13 | 매니저가 시급 INSERT 시도 | 통과 (거부) |
| 14 | 매니저가 담당 매장 근무 승인 | 통과 |

프로젝트 생성 후 실제 계정 2개로 한 번 더 확인하는 것을 권장한다.
